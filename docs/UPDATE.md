# Обновление существующего бота с сохранением данных

1. Запишите текущую версию кода и остановите бот. Не запускайте старый и новый процесс одновременно. Не применяйте `git reset --hard` к локальным изменениям.
2. Сохраните приватную копию каталога с текущим кодом, `bot.env` и базой. Если SQLite работала в WAL, предпочтителен backup API, либо копирование всего каталога только после остановки всех соединений, включая `.db-wal` и `.db-shm`. Не загружайте архив в Git/чат.
3. Обновите исходники согласованным способом, сохранив `bot.env`. Сравните настройки с `bot.env.example`; добавьте политику, реального оператора данных и явные ID сотрудников. Старый встроенный администратор больше не действует.
4. Создайте новое venv Python 3.12 или обновите существующее: `.venv\Scripts\python.exe -m pip install -r requirements-lock.txt`. На Linux — `.venv/bin/python`.
5. Выполните `run.py --check-config` и `python -m unittest discover -s tests -v`. Для прогона миграции на копии задайте `DB_PATH` в процессе: `$env:DB_PATH = 'C:\private\migration-test.db'`; затем `python maintenance.py migrate`. Переменная процесса имеет приоритет над файлом! После проверки удалите override через `Remove-Item Env:DB_PATH`.
6. Для настоящей базы выполните `python maintenance.py migrate`. Перед переходом с исходной схемы создаётся новая согласованная копия в `backups/`, с проверкой `PRAGMA integrity_check`. Изменения схемы — в одной транзакции, версия `PRAGMA user_version=2`. Записи сохраняются, старые статусы не переписываются. При неподдерживаемой схеме миграция откатывается и требует отдельного анализа, а резервная копия остаётся.
7. Запустите `python run.py`. В тестовом личном чате пройдите реальную заявку, проверьте CRM, смену статуса, `/stats`, `/export`. Эти сетевые проверки нельзя заменить локальными тестами. Существующие незавершённые формы до обновления начните заново через `/menu`.
8. Проверьте `/delivery`. Прерванные отправки переходят в `проверить` после истечения 10 минут. Сначала найдите карточку в CRM. Лишь если повторная отправка действительно нужна, выполните `/retry_delivery ID CONFIRM` в личном чате администратора.
9. Установите регламент обработки `/delete_me` и обезличивания, хранения резервных копий и выгрузок. Не удаляйте рабочую базу ради «чистого запуска».

Откат: остановите новую версию; сохраните её базу и WAL/резервную копию, чтобы не потерять заявки после обновления. Для запуска старой версии используйте соответствующую проверенную резервную копию в отдельном приватном каталоге. Не заменяйте новую базу старой вслепую: заявки, поступившие после миграции, требуют сохранения/согласованного переноса. Автоматический откат поверх новых заявок не реализован.
